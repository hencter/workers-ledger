## 二、退出码约定

三个脚本共用一套退出码语义，自测逐个验证：

| 退出码 | 含义 | 是否受 `--check` 影响 |
| --- | --- | --- |
| 0 | 通过；默认报告模式跑完也是 0 | 否 |
| 1 | 校验发现问题 | 是。默认报告模式只报告不失败；`--check` 才非零退出 |
| 2 | 运行环境错误（输入缺失、解析不到任何记录、文件读不了） | 否。两种模式都非零退出 |

`--check` 下什么算失败，按脚本分别定：

- 条目结构：「错误」档失败；「警告」档要加 `--strict` 才失败；「提示」档永不失败。
- 信源监控：只对「确定失效」和「版本不一致」失败。超时、连不上、5xx、TLS 握手失败、403、疑似版本不一致、注册表缺字段都不失败。
- 脱敏扫描：个人信息类「硬命中」失败；需语境档要加 `--strict` 才失败。

### 3.3 真实正文（正例）

```
> node tools\check-items.mjs --root . --check
```

实测（复核时仓库里已有 10 个正文文件、166 条条目；队友仍在并行补写正文，数字会随正文增长变动）：

```
文件 10 个，条目 166 条
错误 0 项（含待复核 0 项），警告 26 项（含未定稿 16 项），提示 31 项
[通过] 条目结构校验通过：错误 0 项，警告 26 项（退出码 0）
```

**退出码**：`0`，符合预期。「警告 26 项（含未定稿 16 项）」不是失败，是如实标出「还没追到官方原文、按 AGENTS.md 底线一标了『待核实』」的条目——这类条目会出现在 `GITHUB_STEP_SUMMARY` 里，供发布前清点；加 `--strict` 即变成非零退出，可当发布门禁用。

这也验证了脚本对真实正文里的三种写法都能正确处理：

1. 枚举值带行内强调：`- 举证难度：**难**——…` 能取出「难」；
2. 效力位阶多值并列：`- 效力位阶：法律 + 行政法规 + 司法解释` 三个值逐个校验；
3. 条目之间用 `---` 分隔线，不判为游离行。

## 五、首轮真实联网检查暴露的两处误报，与据此做的修改

这一节是本次自测最重要的产出。**只用桩服务测不出这些问题，只有拿真实政府网页跑才会暴露。**

### 5.1 版本比对把网页元数据当成了法规版本日期

首轮真实联网检查（15 条）报出 **7 条「版本不一致」**，全部是误报。原因：政府网站页面自带元数据块，例如

```html
<h2>发布日期：</h2><p>2008年09月19日</p>
```

那是**网页的发布日期**，不是法规的公布日期，与注册表记录的公布日期相差一两天属常态。原实现把「发布/公布/通过」也当作版本关键词，于是这串日期被当成法规版本，判成「页面有更新的版本」。

**修改**：版本关键词只保留「修正／修订／修改」与「施行／实施／生效」两类，去掉「通过／发布／公布／批准」。这正好回到任务书要求的比对范围——「页面内容显示有更新的**修正或施行**版本」。

修改后同一份信源表复跑：**7 条硬问题全部消失，14 条正常、1 条超时、0 条硬问题**。

### 5.2 关键词与日期配对错位

`修订后自 2011-01-01 施行` 这种写法里，日期左侧是「修订」、右侧是「施行」，原实现按「最近关键词」配对会把「修订」配给这个日期，导致注册表里真正的施行日期丢标签、进而误判。

**修改**：改为按词序配对——优先配日期右侧的第一个关键词，且两者之间不得再夹着别的日期；右侧找不到才回头配左侧。

### 5.3 脱敏扫描把法条用语当成个人自述

用真实正文（`book/01`、`book/02`，以及当时已完成的其余各节）跑，命中 3 处「本人 + 自述动作」，全部是误报：

- 「就不算非因**本人**意愿，所以签**离职**文件时…」——命中「离职」；
- 「**本人**户籍所在地或者经常居住地」——命中「户籍」，这是《职业病防治法》的法定表述；
- 「非因**本人**意愿」取决于**离职**证明…

**修改**：去掉「本人 + 动作动词」这一判据，只认 lead 核定的四类具体信息——**时间、地点、职务、金额**。修改后真实仓库复扫：**需语境档从 3 处降到 0 处**。

### 5.4 同批修正的其他两项

- 「本人 2024 年 3 月入职」原被当成「本人签字」式文书用语吞掉（分隔符里含空格）；已收紧为不含空格。
- 长词与短词的包含关系会重复报（「笔者所在城市」与「笔者」）；已改为长词优先、被包含的短词不再单独报。

### 5.5 公司名规则把「股份有限公司」这个词本身当成了公司名

本自测记录里写「非『有限公司／股份有限公司』形式的单位名称」这句时，扫描器报了「公司全称：股份有限公司」。原因是组织形式词前只要凑够两个字就成匹配：`股份有限公司` 被拆成「股份」+「有限公司」。

**修改**：光秃秃的组织形式词（`股份有限公司`／`有限公司`／`有限责任公司`／`集团有限公司`）与前面只是「股份」「有限」「名称」「单位」「形式」这类通用词的，一律不算公司名。

修改后真实仓库复扫，该误报消失；泄露样例里的虚构公司名仍然照常命中（未削弱检出）。

## 七、工作流自测

`.github/workflows/verify.yml` 三个并行 job（条目结构、来源时效、脱敏扫描），`push` 与 `pull_request` 触发，另有 `schedule: '0 2 * * 1'`（每周一 02:00 UTC，北京 10:00）只跑来源时效的联网全量检查，外加 `workflow_dispatch` 手动触发。

**本机没有可用的 YAML 解析器**（工具链要求零依赖，不能为校验工作流引入 npm 包；本机 Python 环境也没有 yaml 模块）。因此工作流只做了结构性核查，未做语法解析：

| 核查项 | 命令 | 实测 |
| --- | --- | --- |
| 无制表符（YAML 禁用 Tab 缩进） | 逐行匹配 `\t` | 含制表符行数 0 |
| 缩进为偶数空格 | 统计每行前导空格数 | 非偶数行数 0 |
| 工作流引用的脚本都存在 | 提取 `tools/*.mjs` 逐个 `Test-Path` | 3 个全部存在 |
| 触发事件与 job 名 | 提取键名 | `push`/`pull_request`/`schedule`/`workflow_dispatch`；job：条目结构、来源时效、脱敏扫描 |

**未验证**：GitHub Actions 实际执行结果（本机无法触发远端流水线）。这是本次自测唯一未经运行验证的部分，已在第八节列为局限。

工作流里对来源时效 job 的分工：`schedule` 与手动触发的联网开关打开时走联网 `--check`；`push`／`pull_request` 走 `--offline --check`，只校验注册表必填字段——快速且结果稳定，不受境外 runner 连不上 gov.cn 的影响。

## 十、口径调整记录与待规范同步项

自测中发现脚本按规范字面实现会与仓库其他权威文件冲突，已按「规则太紧就改规则」处理，并在此留痕：

| # | 冲突点 | 处理 | 建议 |
| --- | --- | --- | --- |
| 1 | 仓库根 `AGENTS.md` 底线一写明「追不到官方原文的，写『待核实』并说明尝试路径…标一个『待核实』是正确行为」，但 `docs/条目规范.md` 的效力位阶／主张强度／举证难度是封闭白名单，没有「待核实」 | 脚本认「待核实」为**未定稿标记**，按「警告」报出（不判枚举越界、不失败），另加一条「标了待核实但全条目未说明尝试路径」的警告 | 建议在 `docs/条目规范.md` 里把「待核实」写成三个标注栏与「依据」「来源」两栏允许的临时取值，让规范与 AGENTS 一致 |

## 十一、已知局限

**必须如实说明的：**

1. **工作流未经真实执行验证。** 本机没有 YAML 解析器也没有 Actions 运行环境，只做了结构性核查（见第七节）。首次推到远端后需要看一眼三个 job 的实际结果。
2. **境外 runner 上抓不到 gov.cn。** 超时、5xx、TLS 握手失败都归入「没连上」「握手不兼容」两档、不判失效——这是刻意的，否则工作流天天红。代价是：GitHub 托管 runner 上基本抓不到真正的「版本不一致」，要抓必须在能访问 gov.cn 的环境（自建 runner 或本地）跑。工作流注释里已写明这一点。
3. **引用块与代码块默认整体跳过**，块内的敏感串扫不到。这是为压掉法条原文的误报而做的取舍，`--include-quoted` 可开关，跳过行数每次都会统计报出，盲区可见。
4. **版本比对依赖页面静态可达。** 单页应用（如 `flk.npc.gov.cn`）取不到正文，会落到「待人工确认」；这是如实分类，不是漏检，但确实意味着这类来源无法自动监控。
5. **版本比对只覆盖「修正／施行」两类关键词**，且要求页面出现法规名称、日期与关键词相邻。漏报（页面改版、关键词换写法）比误报风险更大——这是刻意选的方向。
6. **脱敏扫描无法识别的形态**：15 位旧身份证号；非「有限公司／股份有限公司」形式的单位名称（如「某某局」「某某中心」）；图片、附件里的信息；姓名本身（除非与手机号、职务等同现）。「地名 + 行业 + 职级」是模糊规则，输出为「需人工判断」。
7. **银行卡号只认现实前缀**（62、4、51–55、34、37、35 开头）。
8. **条目校验只校验「依据」栏有没有书名号**；规范要求的「版本与施行日期」在正文里统一登记于 `sources/法规清单.md`，故脚本改为「提示」档，不做硬性要求。
9. **效力位阶多值并列**（如「法律 + 司法解释」）时，只校验括号外的取值；括号内再写第二个位阶不会被校验。
10. **脱敏扫描的「豁免」机制**：单行含「脱敏扫描豁免」即跳过。豁免行数每次统计报出，但机制本身可被滥用。
11. **180 天待复核**是脚本约定值，不是规范值（见第十节第 5 条）。

## 十二、结论

- 三个脚本在 Node 24 下均可直接 `node tools\xxx.mjs` 运行，零外部依赖，无 `package.json`。
- 15 个回归用例退出码全部与预期一致（0／1／2 三档语义各自验证）。
- 每个脚本的每一条报错路径都用故意造错的样例真实触发过，不是「写了就算」。
- 两处只有真实数据才能暴露的误报（版本比对、脱敏扫描）已修复并复跑验证；修复过程与依据记录在第五节。
- 五处脚本口径与权威文件不一致的地方已按「宁可改规则也不误红」处理，并列出待规范同步项（第十节）。
