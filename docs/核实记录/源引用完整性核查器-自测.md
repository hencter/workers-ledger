**日期**：2026-10-03
**范围**：`tools/check-refs.mjs`（登记 ↔ 依据 ↔ 来源 四方对账）与 `.tmp-refs/` 故意造错夹具
**环境**：Windows，Node v24.19.0，零依赖（无 `package.json`、无 `node_modules`）
**输入快照**：`sources/法规清单.md` 的 git blob 为 `88e4d7523af6dea9f592b41ee20bb91e02d41ab2`；`tools/check-refs.mjs` 的 blob 为 `93db117667db6bb7e2a6b68da1b1b59b523957d7`。**清单是并行编辑的活文件**——本机跑的数以该 blob 为准，换一个 blob 数字会变。本次工作期间清单至少被并行改过两次（工作开始的快照是 `c35f0928…`，其中 N01 换源到 2021 年修订本）；两个快照上六项检查的命中数完全相同，本文记录的数字因此是稳的，但引用到的**行号与单元格内容**以 `88e4d752…` 为准。

本文件记录的是「拿真实仓库与故意造错的样例当场跑一遍」的过程与结果，不是设计说明。凡写「实测」，都是本机跑出来的原始输出。

## 一、这个工具补的是哪一道缺口

`AGENTS.md`「源时效（三层，缺一层就断链）」第 2 层与 `docs/条目规范.md`「来源栏与信源表的分工」都要求：正文「依据」里出现的每一部法规全称，必须能在 `sources/法规清单.md` 找到。

实测缺口：

- `tools/check-items.mjs` 的「依据 ↔ 清单」交叉核查**只在「来源」栏没有 URL 且指向清单时才触发**；
- 而正文 324 条里 **323 条**的「来源」栏直接内嵌 URL、**0 条**按清单编号填写 → 触发条件一次都没成立过，这道锁从未生效；
- `tools/check-sources.mjs` 只检查清单自己那 33 条登记的链接与版本，不看正文引用了什么。

本工具就是补第 2 层：正文「依据」引了哪部法规、该法规在清单里登记的版本是什么、正文「来源」栏的链接与标注是否与清单对得上。**它不联网**（可达性归 `check-sources.mjs`），**不判条文实体内容**（条号归 `sources/条文摘录.md` 的逐字底本）。

实现上刻意**不复用** `tools/check-sources.mjs` 的解析函数（那个脚本注释写明「刻意不复用，复用会让两边同时错」），清单解析独立重写；共享契约只复用 `tools/lib/条目规范.mjs` 的 `parseSectionFile / fieldOf / stripInline / urlsIn / entryLabel / listBookFiles`。

### 4.1 夹具暴露并修掉的两个真问题

**问题一（编码错误）：引用名取成了 `undefined`。** 抽取书名号内容时把对象当匹配数组用（`mk[1]` 应为 `mk.raw`），`norm` 正常所以匹配结果全对，检查项 1/3 的错误信息模板里 `《${c.raw}》` 会打印成 `《undefined》`。真实仓库恰好检查项 1 命中 0 项、检查项 3 当时也命中 0 项，这个 bug 在真实数据上是隐形的；是夹具第一次报出未登记引用时才现形的。修好后夹具与真实仓库都复跑通过。

**问题二（误报）：网址路径里的 `A02` 被当成清单编号。** 真实仓库首次运行，检查项 5 报出 2 条「编号 A02 不存在」——`A02` 其实是 `moe.gov.cn/srcsite/A02/s5911/…` 路径段。修法：扫编号前先把 URL 抠掉（`maskUrls`），再在新文本上匹配。修好后真实仓库检查项 5 归零。

## 六、323 条来源栏的迁移量估算（只估算，未动手）

### 6.2 结论

- **判断面是 42 + 6 + 13 + 4，不是 323。** 42 个不同 URL 的映射决定下来之后，其余是机械替换；6 个未登记域名要先补登记；13 条要先补依据；4 条要先修版本。

- **不要顺手批量改。** `AGENTS.md` 已写明「迁移要另行决定，不要顺手批量改」，本工具只报数，不做任何自动改写。

## 八、口径决定与已知局限

**口径决定（都在源码注释里写明出处）**：

1. **检查项 1 的匹配**：去空格、去书名号归一化后先做精确全等；不中再双向子串容错（清单全称含引用简称，或反之）；多个容错候选取「与引用名长度差最小」。
2. **检查项 3 的两段规则**：① 同类关键词（修正/施行）逐年比，正文早于清单即错误；② **兜底**——同类配不上对时，拿「本条所引同一登记记录的多个引用窗口合并后的最大年份」比清单「现行版本」栏的最大年份，落后即错误。第 ② 段是清单并行换源到 N01 2021 年本之后逼出来的：两侧年份都不是修正/施行关键词，第 ① 段完全看不到。
3. **检查项 4 的判据**：URL 域名不在清单**任何一条**登记的域名内。最保守、零误报；严口径（是否属本条所引法规）单列为 E4。
4. **检查项 5 先抠 URL**：网址路径里的 `A02` 这类片段不是编号，见 4.1 问题二。
5. **检查项 6 的标注位置**：在「核验状态」与「URL」两列上找标注。约束原文说的是核验状态列，放宽到 URL 列是因为清单里带「转载页」字样的括注出现在 URL 列；实际两侧都要求整句「转载页，待换一手源」。
6. **不联网、不判实体**：可达性与页面版本归 `check-sources.mjs`；条号是否正确归 `sources/条文摘录.md` 的逐字底本。

**已知局限（必须如实说明）**：

1. **域名级判据，看不到路径差异。** 同域名不同路径不算问题（`www.court.gov.cn/fabu/…` 与 `www.court.gov.cn/zixun/…` 都放过）。这类「同源不同页、页面内容对不上」要靠人工或 `check-sources.mjs` 的联网比对。
2. **检查项 6 的口径偏窄。** 清单里 L01 的 URL 括注写着「转载页」但没写「待换一手源」整句，按本工具的判据不构成「必须保留标注」；若仓库想把 L01 也纳入，需要清单侧把标注写全（这属于清单的写权，不在本任务范围）。
3. **容错匹配可能把引用归到「父」法规。** 嵌套书名号（如《…修改〈工伤保险条例〉的决定》）会落到父法规的登记记录上。这在本仓库是想要的（清单把修改决定链接登记在该条 URL 栏），但换一部法规就可能不成立，属于规则的人工前置。
4. **检查项 3 只认文本里出现、且带分隔符或「年」的 4 位年份。** 文号里的年份（如「国务院令第 375 号」）不参与比对；正文完全不写年份的引用直接跳过（本次 365 条带年份、8 条无法配对，其余 53 条引用无年份）。同一条目里若同时引了新旧两部法规，兜底取的是「该登记记录相关窗口」的最大年份，不做跨法规推断。
5. **检查项 2 只看「依据」栏。** 只在「来源/备注」里出现的法规算「未引用」——这是按清单作为依据注册表的定位，不是漏检。
6. **检查项 4 不验证链接是否活着、页面内容是否对。** 它只回答「这个域名在清单里登记过吗」。
7. **`相关核实记录` 线索有截断**：每个编号最多附 2 行、每个文件最多收 40 行，避免报告被刷屏。
8. **不判断条文实体内容**。本工具报的是「引用关系不一致」，不是「法条写错了」；条号错位一类风险仍由 `sources/条文摘录.md` 与人工审计负责。
9. **数字随清单变化。** 本次快照清单 blob `88e4d752`（另一个快照 `c35f0928` 上六项命中数相同）；同一 blob 下重跑数字一致（运行前后各取一次 `git hash-object`，未变）。清单被并行编辑后请以新快照为准。
10. **参考实现无先例可循。** 本工具是仓里第一个做「正文 ↔ 清单」四方对账的脚本，规则是拿真实数据与夹具反复校准出来的；后续若 `docs/条目规范.md` 对来源栏分工有新的规定，检查项 1/4/5 的判据需要同步。
