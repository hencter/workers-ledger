# 严格构建并入体检：把 WARN 当失败，并纠正一条会 panic 的复现命令

**日期**：2026-10-03
**起因**：核 hugoVersion 时确认「`min` 只产生告警、不是门禁」。要让版本漂移与死模板这类问题真的拦住构建，得把严格构建变成体检里的一道门禁。

## 一、先探针：两条报错路径都逼出来

改之前先测清楚每种组合的实际行为，不靠印象写解析规则：

| 探针 | 结果 |
| --- | --- |
| 死模板 + `--printUnusedTemplates`（**不加** panicOnWarning） | 退出码 0，输出 `WARN  Template /_partials/probe-unused.html is unused, source "…"` |
| `{{ warnf "…" }}`（可达位置）+ `--panicOnWarning` | **退出码 1**，`error calling warnf: …` |
| `{{ warnf "…" }}` 不加 `--panicOnWarning` | 退出码 0，只有一行 `WARN` |
| `--panicOnWarning` **+** `--printUnusedTemplates`，且存在死模板 | **Hugo panic**：`printUnusedTemplatesOnce` 发出的 WARN 被升级成 Go 崩溃，退出码 2，输出整段 goroutine 栈 |

**一次假阴性值得记**：探针 B 第一次把 `warnf` 追加到了 `locale.html` 的 `{{ return }}` 之后——那段代码永远不执行，于是得到「退出码 0」，差点据此得出「`--panicOnWarning` 无效」的错误结论。**探针必须放在可达位置。**

## 二、因此不直接用 --panicOnWarning

它与死模板检测互斥：真出问题时给的是栈回溯而不是问题清单。脚本改为跑一次普通构建、**自己收集 `WARN` 行判失败**——语义与 `--panicOnWarning` 相同，但能逐条点名。

## 三、新增 `tools/check-hugo-strict.mjs`

- 输出到 `.tmp-strict/`，**从不写 `site/public/`**——所以即使有 `hugo server` 在跑（那种情况下 `build-prod.mjs` 会拒绝构建），这一步照样能跑；
- 打印 Hugo 版本行：本仓库的教训是「先看版本行」（见 `部署-EdgeOne版本坑.md` 第一节）；
- 三条断言：退出码 0、产物含 `index.html`、**零条 `WARN`**；
- 挂在 `体检.mjs` 的**生产构建之前**，先便宜地拦住模板问题。

## 四、验证（四条路径实测）

| 场景 | 退出码 | 输出 |
| --- | --- | --- |
| 正常 | 0 | `[通过] 严格构建无任何 WARN` |
| 故意放死模板 | 1 | 列出 `/_partials/probe-unused.html` |
| 故意 `warnf` | 1 | 列出该条 `WARN` |
| 移除探针后再跑 | 0 | 恢复通过 |

接入后 `node tools/体检.mjs --full` 共 **10 步**，本次退出码 0。其中「生产构建」因检测到有 `hugo server` 在跑而被跳过（AGENTS.md 的既定门禁）——**恰好验证了这一步的价值**：被挡住的是生产构建，严格构建照跑。

## 五、纠正一处会 panic 的复现命令

`docs/核实记录/前端-hugo站点.md` 第 10 节的复现命令原本写的是：

```bash
hugo --ignoreCache --panicOnWarning --printPathWarnings --printUnusedTemplates --printI18nWarnings
```

写它的时候站点上没有死模板，所以从未暴露问题。**但这条命令一旦遇到死模板就会 panic**（见第一节最后一行）。已在原处改为指向 `node tools/check-hugo-strict.mjs`。

## 六、未做

- `--panicOnWarning` 没有被采用，理由见第二节；若将来 Hugo 修掉那个 panic，可以再考虑两条并用。
- 严格构建**不校验版本**：`min` 的告警只有在旧版 Hugo 上才会出现，而本机是 0.167。要真正拦住版本漂移，仍取决于四条部署路径各自的版本锁定（见 `部署-EdgeOne版本坑.md` 第八节）。
